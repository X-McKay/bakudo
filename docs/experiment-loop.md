# The experiment loop

**Audience:** conceptual overview of bakudo's experiment substrate. The
canonical vocabulary is in [environment-model.md](environment-model.md) and
artifact ownership is in
[task-corpus-and-bundles.md](task-corpus-and-bundles.md).

---

## 1. What bakudo is

Bakudo is a durable meta-agent system: it versions agents, runs them in
sandboxes, evaluates controlled episodes, and promotes improved versions
through a canary. Its identity is:

> **Bakudo runs reproducible experiments on software agents and software
> artifacts, accumulates evidence over time, and promotes only
> independently demonstrated improvements.**

Everything is organized around **one loop**, not three subsystems:

```
     define scenario ──► characterize baseline ──► research ──► improve
            ▲                                   (hypothesize)  (candidates)
            │                                                      │
     new tasks                                                 ▼
     from failures  ◄── promote / no-change ◄── verify ◄── evaluate (paired
            ▲                                  (independent)     experiment)
            └──────────────── evidence ────────────────────────────┘
```

The loop is generic; only the *subject* changes. `ExperimentSpec.subject` is
an explicit discriminator with two bindings: **agent specs** use task-backed
`TrialRecord` observations, while **software artifacts** use workload-backed
`MeasurementRecord` observations. Both normalize into the same named-metric
statistics/reporting layer without conflating their evidence types. The
`research` and `improve` stages (hypothesis generation, candidate mutation)
are deliberately explicit empty slots: their inputs (evidence objects) and
outputs (provenance, lineage) are contracts today; the generators plug in
without changing the loop.

The primitives that carry the loop:

| Primitive | What it is | Where it lives |
|---|---|---|
| **TaskSpec** | A versioned, reproducible environment: instruction + fixture + privileged verifier inputs + reference solution + constraints | Private corpus and published bundles |
| **Trial** | The immutable measurement of one agent × task × seed episode, pinned to exact versions of everything | Postgres (insert-only) |
| **WorkloadSpec** | A versioned, shell-free exercise for measuring one software repository revision, including environment, metric, schedule, and profiler declarations | Private corpus or immutable published bundle |
| **MeasurementRecord** | Raw, uninstrumented samples from one workload × revision × environment pin | Postgres (insert-only) |
| **ExperimentObservation** | Subject-neutral metric envelope whose evidence is explicitly either a `TrialRecord` or a `MeasurementRecord` ID | In-process analysis input; IDs retained in results |
| **Experiment** | A paired baseline-vs-candidate observation matrix with honest statistics — or, only for a candidate-free agent subject, a behavioral profile | Postgres (spec + result) |

## 2. A task, concretely

A task is a directory — authored by a human or generated by a coding agent —
that fully defines a controlled task environment:

```
bakudo-benchmarks/tasks/duplicate-webhook-delivery/
  task.yaml       instruction, environment, limits, verifier, constraints
  fixture/          a small real project with a planted race condition
  verifier/         privileged inputs: fail-to-pass (detect the bug) and
                    pass-to-pass (guard against regressions)
  reference/        the ground-truth patch proving the task is solvable
```

The corpus covers four families:

- **debugging** — planted bugs with verifier regression tests;
- **no-change** — code where the correct action is to change nothing.
  Each no-change task declares a `pairedTask` that points to a
  near-identical sibling that genuinely needs a fix, and the pair is
  scored jointly — so an agent can't score well by blanket refusal, and
  can't score well by always "fixing" something either;
- **adversarial-context** — the issue text names a plausible but wrong
  root cause, the README misleads, an irrelevant error dominates the
  logs. This family measures *how agents fail*;
- **safety / scope-discipline** — tempting out-of-scope edits,
  instructions embedded in repo content, denied-command handling. Real
  behavioral tests, not questionnaires, because abox makes actually
  attempting the unsafe thing safe to observe.

The format is deliberately unoriginal: directory-isomorphic to Harbor's task
format (the terminal-bench standard, so converters are trivial) and
field-compatible with the SWE-bench instance schema. Bakudo invents the
minimum.

**Tasks are code-reviewed like code but validated like data.**
`bakudo task verify` proves, mechanically: the manifest is schema-valid;
provisioning is byte-deterministic; the fail-to-pass tests fail on the
pristine fixture and pass with the reference patch; the regression guards
pass on both; known plausible-but-wrong fixes are rejected; and the
instruction doesn't leak the solution. Published benchmark suites have
repeatedly been shown to contain large fractions of structurally broken
tasks; a task that passes `verify` is structurally sound *by construction* —
which is what makes it safe to let coding agents write tasks autonomously.

## 3. A trial, concretely

```
bakudo trial run duplicate-webhook-delivery --agent debugger@17 --seed 3
```

What happens:

1. **Provision.** The fixture is materialized into a throwaway git repo
   — same task + seed ⇒ byte-identical repo, every time.
2. **Run.** The existing agent-run machinery takes over unchanged:
   Temporal workflow, abox microVM, budgets enforced in-guest, cancel
   racing, the ledger recording every phase. The task can only
   *tighten* the agent's budgets and network access, never loosen them.
3. **Evaluate independently.** The agent's diff — the only artifact
   trusted from the sandbox — is applied to a *fresh* copy of the
   pristine fixture; the verifier tests are copied in; a new
   network-isolated guest runs them and writes named metrics. The
   agent's sandbox never saw the verifier tests, and the grading process
   is out-of-process from the agent — an exit-code escape or a doctored
   test log can't fake a pass.
4. **Evaluate integrity.** Every trial evaluates hard constraints separately
   from reward: did the diff touch privileged verifier inputs, did the agent
   retry denied actions, or did it edit outside the declared scope? Integrity
   violations feed a hard experiment gate.
5. **Persist.** The Trial row embeds a `TaskPin`: source URI, corpus revision,
   task version, bundle digest, and verifier digest. It also records the
   episode ID, seed, bakudo version, abox version, model ID and endpoint,
   guest profile — plus cost (tokens, tool calls, duration) as first-class
   columns, the scorecard, and the verifier-test rates.

A trial is therefore *reproducible* (rerun the pins) and *comparable*
(two trials differing only in agent version are a legitimate paired
observation).

## 4. Experiments, concretely

`ExperimentSpec` always nests subject-specific fields under `subject`:

```yaml
subject:
  kind: agent-spec
  baseline: debugger@17
  candidates: [debugger@18]
  taskSelector: {families: [debugging], count: 20}
```

### Agent-spec experiment

```
bakudo experiment compare debugger@17 debugger@18 --family debugging --count 20
```

1. **Design.** Twenty debugging tasks are selected (holdout partition
   excluded unless explicitly requested — and that exposure is stamped on the
   result forever). For each task × repetition, one baseline trial and one
   candidate trial share a deterministically derived seed. Same worlds, same
   seeds — the only variable is the agent.
2. **Execute.** Trials fan out with bounded concurrency under the existing
   governance (budgets, caps). A crashed trial is a recorded failed trial,
   not a lost data point.
3. **Analyze.** One statistical recipe: average repetitions within each task,
   form per-task paired differences, report the mean delta with a 95%
   bootstrap confidence interval — always the interval, never a bare verdict.
   The result persists a deterministic analysis seed (with separate derived
   streams per candidate and metric), so the interval can be replayed exactly.
   Two honesty rules: deltas smaller than the declared tie zone are **ties**,
   and ties resolve toward the *cheaper* agent. An agent candidate also needs
   at least five distinct task pairs by default (`decision.minPairedObservations`);
   repetitions do not inflate this evidence count. Any safety regression or
   integrity violation ⇒ ineligible, regardless of capability.
4. **Report.** Win/loss/tie counts, per-family deltas ("clean debugging
   unchanged; misleading-hypothesis tasks +18pp" — the counterfactual view
   that tells you *what to fix next*), paired-task joint scores, cost deltas,
   and an advisory promotion verdict.

**Behavioral agent profiling is the same machine with zero candidates.**
`bakudo experiment profile debugger@17` runs the corpus single-arm and emits
the behavioral fingerprint — per-family success, failure structure, cost
profile, and integrity results. That fingerprint is what a
hypothesis-generating agent reads before proposing mutations.

This word has a deliberately narrow meaning. `experiment profile` never
captures CPU samples, call stacks, allocations, or process counters. Those are
diagnostic `PerformanceSnapshot` artifacts produced by
`bakudo performance capture` and are never admitted into selection timing.

### Software-artifact experiment

A software-artifact subject replaces agent/task arms with immutable revision
pins and one `WorkloadRef`:

```yaml
subject:
  kind: software-artifact
  repository: payments-service
  baseline: {repository: payments-service, sourceURI: file:///srv/repos/payments-service, commitSHA: "...", treeDigest: "sha256:...", dirty: false}
  candidates:
    - {repository: payments-service, sourceURI: file:///srv/repos/payments-service, commitSHA: "...", treeDigest: "sha256:...", dirty: false}
  workloadRef: {name: checkout-latency, version: 1.2.0, source: bundle}
metrics:
  primary: latency_seconds
  directions: {latency_seconds: lower}
```

`bakudo experiment run artifact.yaml` and `POST /experiments` use the same
subject-binding port. The synchronous operator path resolves
`BAKUDO_WORKLOAD_SOURCE` (or the packaged smoke corpus), requires the pinned
environment in `BAKUDO_PERFORMANCE_ENVIRONMENT`, and measures in fresh abox
guests. The Temporal path resolves the workload and environment in activities,
then fans out durable measurement children with exact source, workload,
revision, and environment pins.

Artifact observations retain only persisted `measurementId` evidence. Missing,
failed, corrupt, incompatible, direction-mismatched, or integrity-invalid
measurements are contagious: the affected comparison is inconclusive and
ineligible rather than converted to zero or silently dropped. Artifact
subjects must have at least one candidate and cannot use task-reward metrics.
Diagnostic capture remains separate from experiments.

**Promotion is two-stage.** Offline experiments are *screening* (pick the
best candidate); the canary is the *confirmatory* stage (one pre-registered
comparison on live traffic). This dissolves the multiple-comparisons problem
structurally instead of statistically.

## 5. Designed for autonomous operation

The substrate is built so that coding agents can operate the loop:

- **Generation.** `bakudo task scaffold NAME --family FAMILY --root PATH`
  emits a commented template in a writable corpus (canary strings and
  provenance pre-filled); every command speaks `--json`; every validation
  error carries a JSON-pointer path and a remediation hint. An agent can
  draft → verify → fix → verify in a tight mechanical loop. ExperimentSpecs
  and candidate AgentSpecs are plain schema-validated YAML — the artifact
  type agents generate most reliably.
- **Trust.** Agent-generated and imported tasks are fail-closed:
  `eligibleForPromotion: false` until verified, generator identity recorded,
  and a generator's tasks can't immediately promote the generator's own
  lineage (anti-poisoning).
- **Contamination discipline.** Anything public is assumed memorized, so
  imported tasks live in the dev split only. Holdout tasks are freshly
  authored. Every fixture embeds canary strings so future contamination is at
  least detectable.
- **The one hard boundary.** The measurement plane — graders, verifier tests,
  statistics, promotion logic — is outside every mutable surface: not
  reachable from AgentSpec mutations, not present in the sandbox. The most
  damaging documented failure of self-improving systems is evaluator
  sabotage; bakudo's design makes it *structurally impossible* rather than
  merely discouraged, and this property is a named, regression-tested
  invariant.

## 6. Deployment model: a resident system, not a per-repo tool

Bakudo is a **standing service**, not a CLI you run inside a repository. The
control plane stays up — the meta-agent entity workflow holding
backlog/budgets across cycles, the repo observer, the Temporal worker, the
API, Postgres/FalkorDB — and it operates on a *portfolio* of repositories
that live on the host. Everything distinctive about it (durable curriculum,
canary routing across runs, accumulated memory, the experiment ledger) is
longitudinal state that a per-repo tool invocation would throw away. The
tool-style entry points (`bakudo demo`, the sync mirrors) remain as dev/CI
conveniences.

Repository onboarding is deliberate:

```
bakudo repo add https://github.com/acme/payments-service   # clones into the managed root
bakudo repo add ~/git/inference-gateway --name gateway     # registers an existing checkout
bakudo repo list --json
bakudo repo remove gateway                                 # deregisters; never deletes files
```

Registered repos are recorded in the ledger (name, source, path, base ref,
provenance) and objective resolution consults the registry first, falling
back to the `$BAKUDO_REPO_ROOT` directory convention. Cloning fetches data
only — repository code still executes exclusively inside sandbox guests. Task
fixtures are unaffected either way: the provisioner materializes those
itself.

## 7. Extension points

The loop's empty slots and ports define where the system grows without
changing its vocabulary:

- **Mutation + lineage.** Single-factor candidate mutations proposed from
  profile fingerprints, with archive/diverse-parent selection and
  lineage-aware scoring, plug into the `research`/`improve` slots.
- **Statistical promotion.** `PromotionPolicy` can require an
  `ExperimentResult` as promotion evidence, with successive-halving shapes
  for large candidate sets.
- **Remote environments.** External environment frameworks integrate at the
  existing ports — task discovery behind `TaskSource`, execution behind the
  sandbox boundary, grading behind `VerifierRunner`, and remote performance
  execution behind `MeasurementRunner`/`WorkloadInvoker` — without a second
  evidence vocabulary.
- **Task factory.** Failed production runs become minimized, verified tasks;
  the verify loop already accepts machine-generated input.
- **Teams.** TeamSpec topologies as experiment subjects — "is a critic worth
  the extra cost?" becomes an experiment, not an opinion.

The through-line: **measurement first, autonomy second** — each autonomy
increment lands on an apparatus that can tell whether it actually helped.
