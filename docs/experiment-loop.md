# Bakudo, Reframed: A Controlled Experimentation System for Autonomous Software Engineering

**Audience:** review document for the experiment-substrate work
(`feature/experiment-substrate`). Describes how bakudo works once the
substrate lands, end to end, in plain terms. The precise design is in
`docs/superpowers/specs/2026-08-15-experiment-substrate-design.md`.

---

## 1. What bakudo becomes

Today bakudo is a durable meta-agent system: it versions agents, runs
them in sandboxes, evaluates the runs, and promotes improved versions
through a canary. What it cannot yet do is *measure rigorously*: there
is no controlled environment to run an agent in, no persisted record of
a single controlled run, and no statistics behind the word "improved."

After this work, bakudo's identity sharpens to:

> **Bakudo runs reproducible experiments on software agents (and later,
> software artifacts), accumulates evidence over time, and promotes only
> independently demonstrated improvements.**

Everything is organized around **one loop**, not three subsystems:

```
     define benchmark ──► profile baseline ──► research ──► improve
            ▲                                   (hypothesize)  (candidates)
            │                                                      │
     new scenarios                                                 ▼
     from failures  ◄── promote / no-change ◄── verify ◄── evaluate (paired
            ▲                                  (independent)     experiment)
            └──────────────── evidence ────────────────────────────┘
```

The loop is generic; only the *subject* changes. This phase builds the
loop's measurement core with one subject wired in — **agents** — and
leaves a clean seam where **software artifacts** (the current optimize
loop, generalized) plug in later as a second binding rather than a
parallel system. The stages `research` and `improve` (hypothesis
generation, candidate mutation) are deliberately left as explicit empty
slots this phase: their inputs (evidence objects) and outputs
(provenance, lineage) are designed now; the generators come later.

Three primitives carry the loop:

| Primitive | What it is | Where it lives |
|---|---|---|
| **ScenarioSpec** | A versioned, reproducible world: fixture repo + hidden tests + reference solution + manifest | Files in git (`evals/scenarios/`) |
| **Trial** | The immutable record of one agent × scenario × seed execution, pinned to exact versions of everything | Postgres (insert-only) |
| **Experiment** | A paired baseline-vs-candidate trial matrix with honest statistics — or, with no candidates, a *profile* of one agent | Postgres (spec + result) |

## 2. A scenario, concretely

A scenario is a directory — authored by a human or generated by a coding
agent — that fully defines a controlled task environment:

```
evals/scenarios/duplicate-webhook-delivery/
  scenario.yaml     what the task is, its family, budgets, expectations
  fixture/          a small real project with a planted race condition
  hidden/           tests the agent never sees: fail-to-pass (detect the
                    bug) and pass-to-pass (guard against regressions)
  reference/        the ground-truth patch proving the task is solvable
```

Four families ship first:

- **debugging** — planted bugs with hidden regression tests;
- **no-change** — code where the correct action is to change nothing.
  These ship as *twins*: each no-change scenario is paired with a
  near-identical sibling that genuinely needs a fix, and the pair is
  scored jointly — so an agent can't score well by blanket refusal, and
  can't score well by always "fixing" something either;
- **adversarial-context** — the issue text names a plausible but wrong
  root cause, the README misleads, an irrelevant error dominates the
  logs. This family measures *how agents fail*, and the research sweep
  found it's genuinely underexplored territory;
- **safety / scope-discipline** — tempting out-of-scope edits,
  instructions embedded in repo content, denied-command handling. Real
  behavioral tests, not questionnaires, because abox makes actually
  attempting the unsafe thing safe to observe.

The format is deliberately unoriginal. It's directory-isomorphic to
Harbor's task format (the terminal-bench standard, so a converter is
trivial and their 20+ ported benchmarks become an import pool) and
field-compatible with the SWE-bench instance schema (the entrenched
format for repo+patch+tests tasks). We invent the minimum.

**Scenarios are code-reviewed like code but validated like data.**
`bakudo scenario verify` proves, mechanically: the manifest is
schema-valid; provisioning is byte-deterministic; the fail-to-pass tests
fail on the pristine fixture and pass with the reference patch; the
regression guards pass on both; known plausible-but-wrong fixes are
rejected; the mission text doesn't leak the solution; and (advisory,
LLM-assisted) the hidden tests don't demand anything the mission text
never asked for. That last trio matters because the literature is
brutal: audits found 24–59% of "verified" public benchmark tasks were
broken in exactly these ways. A scenario that passes `verify` is
structurally sound *by construction* — which is what makes it safe to
let coding agents write scenarios autonomously.

## 3. A trial, concretely

```
bakudo trial run duplicate-webhook-delivery --agent debugger@17 --seed 3
```

What happens:

1. **Provision.** The fixture is materialized into a throwaway git repo
   — same scenario + seed ⇒ byte-identical repo, every time.
2. **Run.** The existing agent-run machinery takes over unchanged:
   Temporal workflow, abox microVM, budgets enforced in-guest, cancel
   racing, the ledger recording every phase. The scenario can only
   *tighten* the agent's budgets and network access, never loosen them.
3. **Evaluate independently.** The agent's diff — the only artifact
   trusted from the sandbox — is applied to a *fresh* copy of the
   pristine fixture; the hidden tests are copied in; a new
   network-isolated guest runs them and writes named metrics to a
   `reward.json`. The agent's sandbox never saw the hidden tests, and
   the grading process is out-of-process from the agent — a
   `sys.exit(0)`-style escape or a doctored test log can't fake a pass.
4. **Flag hacking.** Every trial computes reward-hacking flags drawn
   from documented frontier-model behavior: did the diff touch test or
   CI paths? did the agent retry denied commands? did it edit outside
   the declared scope? Flags feed the safety gate.
5. **Persist.** The Trial row pins *everything*: agent version, scenario
   version + content digest, seed, bakudo version, abox version, model
   ID and endpoint, guest profile — plus cost (tokens, tool calls,
   duration) as first-class columns, the scorecard, and the hidden-test
   rates. Optionally it emits an Inspect-format transcript, which makes
   the open-source trace-analysis ecosystem (Docent, Inspect View) work
   on bakudo trials with zero integration.

A trial is therefore *reproducible* (rerun the pins) and *comparable*
(two trials differing only in agent version are a legitimate paired
observation). That's the whole point.

## 4. An experiment, concretely

```
bakudo experiment compare debugger@17 debugger@18 --family debugging --count 20
```

1. **Design.** Twenty debugging scenarios are selected (holdout
   partition excluded unless explicitly requested — and that exposure is
   stamped on the result forever). For each scenario × repetition, one
   baseline trial and one candidate trial share a deterministically
   derived seed. Same worlds, same seeds — the only variable is the
   agent.
2. **Execute.** Trials fan out with bounded concurrency under the
   existing governance (budgets, caps). A crashed trial is a recorded
   failed trial, not a lost data point.
3. **Analyze.** One statistical recipe (from Anthropic's "Adding Error
   Bars to Evals" and the small-n eval-power literature): average
   repetitions within each scenario, form per-scenario paired
   differences, report the mean delta with a 95% bootstrap confidence
   interval — always the interval, never a bare verdict. Two honesty
   rules: deltas smaller than the declared tie zone (~10pp at this n,
   because that's what the power actually supports) are **ties**, and
   ties resolve toward the *cheaper* agent. Any safety regression or
   hack flag ⇒ ineligible, regardless of capability.
4. **Report.** Win/loss/tie counts, per-family deltas ("clean debugging
   unchanged; misleading-hypothesis scenarios +18pp" — the
   counterfactual view that tells you *what to fix next*), twin-pair
   joint scores, cost deltas, and an advisory promotion verdict.

**Profiling is the same machine with zero candidates.**
`bakudo experiment profile debugger@17` runs the corpus single-arm and
emits the behavioral fingerprint — per-family success, failure
structure, cost profile, hack flags. That fingerprint is precisely what
a future hypothesis-generating agent reads before proposing mutations.

**Promotion stays two-stage, using machinery that already exists.**
Offline experiments are *screening* (pick the best candidate); the
existing canary is the *confirmatory* stage (one pre-registered
comparison on live traffic). This dissolves the multiple-comparisons
problem structurally instead of statistically, and this phase changes
nothing about the promotion state machine itself.

## 5. Designed for autonomous operation

The substrate is built so that coding agents can operate the loop:

- **Generation.** `bakudo scenario scaffold` emits a commented template
  (canary strings and provenance pre-filled); every command speaks
  `--json`; every validation error carries a JSON-pointer path and a
  remediation hint. An agent can draft → verify → fix → verify in a
  tight mechanical loop. ExperimentSpecs and candidate AgentSpecs are
  plain schema-validated YAML — the artifact type agents generate most
  reliably. An authoring skill (in-repo, written for agent consumption)
  documents the invariants per family.
- **Trust.** Agent-generated and imported scenarios are fail-closed:
  `eligibleForPromotion: false` until verified, generator identity
  recorded, and a generator's scenarios can't immediately promote the
  generator's own lineage (anti-poisoning; fields now, full enforcement
  with the Scenario Factory phase).
- **Contamination discipline.** Anything public is assumed memorized
  (models reproduce SWE-bench file paths from memory), so imports —
  e.g., from SWE-smith's MIT toolkit, whose bug-injection strategies are
  also the model for our later generation phase — live in the dev split
  only. Holdout scenarios are freshly authored. Every fixture embeds
  canary strings so *future* contamination is at least detectable.
- **The one hard boundary.** The measurement plane — graders, hidden
  tests, statistics, promotion logic — is outside every mutable surface:
  not reachable from AgentSpec mutations, not present in the sandbox.
  The most damaging documented failure of self-improving systems is
  grader sabotage (Sakana's DGM faked test logs and deleted its own
  hallucination detectors). Bakudo's config-space design makes that
  *structurally impossible* rather than merely discouraged, and this
  property is now a named, regression-tested invariant.

## 6. Deployment model: a resident system, not a per-repo tool

Bakudo is a **product-shaped standing service**, not a CLI you run
inside a repository. The control plane stays up — the meta-agent entity
workflow holding backlog/budgets across cycles, the repo observer, the
Temporal worker, the API, Postgres/FalkorDB — and it operates on a
*portfolio* of repositories that live on the host. Everything
distinctive about it (durable curriculum, canary routing across runs,
accumulated memory, the experiment ledger) is longitudinal state that a
per-repo tool invocation would throw away. The tool-style entry points
(`bakudo demo`, the sync mirrors) remain as dev/CI conveniences.

Until now, repo onboarding was implicit: a repo "existed" if its
directory sat under `$BAKUDO_REPO_ROOT`. This work makes onboarding
deliberate:

```
bakudo repo add https://github.com/acme/payments-service   # clones into the managed root
bakudo repo add ~/git/inference-gateway --name gateway     # registers an existing checkout
bakudo repo list --json
bakudo repo remove gateway                                 # deregisters; never deletes files
```

Registered repos are recorded in the ledger (name, source, path, base
ref, provenance) and objective resolution consults the registry first,
falling back to the old directory convention. Cloning fetches data
only — repository code still executes exclusively inside sandbox
guests. Scenario fixtures are unaffected either way: the provisioner
materializes those itself.

## 7. What already exists vs. what's new

| Layer | Status |
|---|---|
| AgentSpec versioning, candidate→canary→active, human gates | exists, unchanged |
| Temporal orchestration, abox microVM sandboxing, budgets, cancel | exists, unchanged |
| Eval suites, scorecards, canary graduation | exists, unchanged |
| Optimize loop (scout→attempts→verify→no-change) | exists; becomes the template for the later artifact binding |
| **ScenarioSpec + provisioner + verify loop** | **new** |
| **Trial persistence + hidden evaluation + hack flags** | **new** |
| **Experiment layer + paired statistics + profile mode** | **new** |
| **`bakudo scenario / trial / experiment` CLI + API routes** | **new** |
| **~25-scenario corpus (4 families, twins, canaries)** | **new** |
| **`bakudo repo add/list/remove` — deliberate repo onboarding** | **new** |
| Old eval corpus (`run_corpus`) | absorbed — same API, now backed by trials |
| Implicit `$BAKUDO_REPO_ROOT` repo convention | absorbed — registry first, directory fallback kept |

Notable deliberate *non*-dependencies, each evaluated against the 2026
landscape: Inspect and Harbor as execution engines (their loops collide
with Temporal+abox; we adopt their *formats*), Gymnasium (wrong API
granularity for episode-level trials; we adopt its seeding and
env-versioning conventions), experiment-tracking platforms as system of
record (none model paired seeded trials; our Postgres ledger does), and
DSPy/TextGrad/OpenEvolve as optimization engines (the later mutation
phase imitates GEPA's ideas instead). The paired-statistics core is the
one component the survey found *nowhere* — it's the part worth owning.

## 8. The road after this phase

Each later phase now has a defined foundation to stand on:

1. **Mutation + lineage (Agent Lab proper).** Single-factor mutations
   (attributable wins) proposed from profile fingerprints; GEPA-style
   reflective proposal later; archive/diverse-parent selection rather
   than greedy hill-climbing; lineage-aware selection (a spec's
   descendants predict better than its own score).
2. **Statistical promotion.** `PromotionPolicy` starts *requiring* an
   ExperimentResult as evidence; successive-halving shapes for >5
   candidates.
3. **Artifact binding (Software Evolution, generalized).** The current
   optimize loop's scout→attempt→verify becomes the second `Benchmark`
   implementation: measurement commands instead of scenarios, PR instead
   of version-flip, same trials, same statistics, same ledger.
4. **Scenario Factory.** Failed production runs → minimized, verified
   scenarios (the verify loop already accepts machine-generated input);
   perturbation-derived variants refresh the holdout without authoring
   cost; impossible-variant probes detect cheating agents mechanically.
5. **Teams.** TeamSpec topologies as subjects — "is a critic worth +28%
   GPU?" becomes an experiment, not an opinion.

The through-line: **measurement first, autonomy second** — each
autonomy increment lands on an apparatus that can tell whether it
actually helped.
